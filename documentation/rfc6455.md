# What the WebSocket codec enforces of RFC 6455

**Status:** describes what shipped (version 0.0.0).

`ghttp_ws_*` (`ws_frame.h`, `ws_handshake.h`, `ws_conn.h`, `ws_deflate.h`) is
WebSocket as bytes in and bytes out, for a client or a server. It opens no
socket, speaks no TLS, reads no clock: the opening handshake works on the
request and response objects the HTTP/1.1 parser produces and the writer takes,
and the connection starts after it. It does not care what carried the
handshake, so the Extended CONNECT of RFC 8441 will need no change to it
(`ghttp_ws_conn_*` takes only the agreed parameters). Each rule below is
tested; test names in `tests/unit/test_ws_*.cpp` are sentences, and the
Autobahn|Testsuite case numbers they stand for are in the last section.
`make check-oracle` compares the connection and the handshake with
`wsproto`, `websockets` and Go's `gorilla/websocket`, and runs the
Autobahn|Testsuite against it in both directions.

Every decision is taken on the octets the stream holds up to a point and never
on how many a call delivered: a frame header is read an octet at a time through
the stateless parser, uncompressed payload is judged an octet at a time, and a
compressed payload is handed to the decompressor in units of 512 octets of the
frame (and the rest at its end), so that which of its failures comes first does
not depend on where the caller's reads fell. A message is one event, at its
last frame. `test_ws_split.cpp` sweeps every two-way split and every piece
size of each scenario, and the fuzzers cut at points their input chooses.

## Connection errors and close codes

A connection error is returned by `ghttp_ws_conn_feed()` (`ERR_CORRUPT` for a
violation, `ERR_LIMIT` for a limit, `ERR_OOM`); the Close frame carrying the
code (section 7.4) is already in the output; the connection stays failed and
writes nothing more. Queueing that Close is best effort: with no memory to build
it the error is still returned and the output has no Close.

| Close code | When |
| --- | --- |
| 1002 | an unmasked client frame, or a masked server frame; a reserved bit no negotiated extension uses; a reserved opcode; a fragmented or longer-than-125 control frame; a length not in its shortest encoding or with the top bit set; a continuation with nothing to continue; a new message inside a fragmented one; a Close body of one octet; a Close code that may not be sent |
| 1007 | text that is not UTF-8 (at the octet, not at the end of the message; also across fragments and feeds); a Close reason that is not UTF-8; compressed data that is not deflate, or text that inflates to invalid UTF-8 |
| 1008 | more control frames than `max_control_per_interval` in an interval (in the connection's whole life if it is never ticked); an output queue that has reached `max_buffered_bytes` because the caller is not writing it |
| 1009 | a frame over `max_frame_payload`, a message over `max_message_bytes` (after decompression), more fragments than `max_fragments`, a compressed message that arrives as more than the limit plus its overhead, or that inflates by more than `max_expansion_ratio` |
| 1011 | out of memory, or the compressor failing (a bug) |

A limit stops the connection at the frame header when the header alone decides
it (a frame, a message, a fragment count, a compressed size), so the payload
never has to arrive, and at the first octet past the limit when only the data
decides it (an inflating message).

## Enforced

### Handshake (section 4)

- Server (`ghttp_ws_server_handshake`): method GET (405 otherwise, with
  `Allow: GET`), HTTP/1.1 or later (400), exactly one `Host` (400; section 4.2.1), at most one
  `Origin` (400; it is handed to the caller in `GHTTP_WsServerResult`, who must
  judge it: cross-site WebSocket hijacking, section 10.2), `Upgrade` naming `websocket` and
  `Connection` naming `upgrade` as list members, case-insensitively and across
  repeated lines (400), exactly one `Sec-WebSocket-Version` of `13` (400 if
  absent or repeated, 426 with `Sec-WebSocket-Version: 13` if another),
  exactly one `Sec-WebSocket-Key` that is 24 characters of canonical base64 of
  16 octets (400). The response is `101` with `Upgrade`, `Connection` and
  `Sec-WebSocket-Accept` (base64 of the SHA-1 of the key and the GUID, section
  4.2.2), and every refusal is `Connection: close` with `Content-Length: 0`.
- A handshake whose fields total more than `max_handshake_bytes` is refused
  with 431 before it is read. More extension offers or parameters than the
  limits are 400, as is a malformed `Sec-WebSocket-Extensions` or
  `Sec-WebSocket-Protocol`.
- Subprotocols (section 1.9): the client's list must be tokens and repeat none
  (400); the server chooses the first of its own, in its own order, that the
  client offered (names are case-sensitive), or none.
- Client (`ghttp_ws_client_handshake_create`, `_finish`): the request has the
  key (from the kernel generator unless the caller supplies a nonce), version
  13, the offered subprotocols and extensions; the response is accepted only if
  it is `101`, names the upgrade, carries exactly the accept value for the key,
  chooses at most one subprotocol and one that was offered, and chooses only
  extensions that were offered, with parameters the offer allows (section 4.2.2,
  section 9.1). A refusal is a result and not an error.
- `ghttp_ws_is_upgrade_request` says whether a request is one, for a server that
  serves other things on the same path.

### Handshake over HTTP/2 (RFC 8441 sections 4 and 5)

`ghttp_ws_server_handshake_h2`, `ghttp_ws_client_handshake_create_h2` and
`_finish_h2` are the same code path as the HTTP/1.1 ones with these differences,
each enforced and tested; the HTTP/1.1 functions are unchanged.

- The request is a CONNECT whose `:protocol` is `websocket` (case-insensitive;
  405 with `Allow: CONNECT` for another method, 400 for another `:protocol`), with
  exactly one `Host` (the `:authority`), no `Upgrade` and `Connection`.
- No `Sec-WebSocket-Key`: a request that has one is refused with 400 (the
  client builder makes none and draws nothing from the kernel generator), and no
  `Sec-WebSocket-Accept`: a response that has one is refused by the client.
- The response is `200` (the client accepts nothing else), with no `Upgrade`,
  `Connection` or accept value, and a refusal has no `Connection` field (HTTP/2
  has none); the caller ends the stream with the refusal.
- `Sec-WebSocket-Version` is required and 13 (400 if absent or repeated, 426 with
  the field otherwise). Origin, subprotocols and extensions (permessage-deflate
  included) are negotiated by the code the HTTP/1.1 handshake uses, so the
  results agree; a client handshake finishes only on the carrier it began on
  (`GHTTP_ERR_INVALID` otherwise).
- `ghttp_ws_is_h2_request` says whether a request is one.
- A client's target is an origin-form or absolute-form one (the `:path`, or a URL that
  gives `:scheme`, `:authority` and `:path`); `*` and an authority-form target are
  `GHTTP_ERR_INVALID` before the request is touched, and a failure after that leaves it
  as a fresh GET.
- `ws_h2.h` joins the stream to a `GHTTP_WsConn`: DATA in, queued bytes out as
  the windows allow, the closing handshake ended with END_STREAM. END_STREAM or
  RST_STREAM before the handshake completed is an abnormal closure, reported as
  1006 (`ghttp_ws_h2_status()`) - also when one Close has gone and the peer ended the
  stream without answering - and a connection error of the codec keeps its own code. A
  reset after the handshake completed changes nothing. A failure of the h2 connection
  is told to the adapter by the caller (`ghttp_ws_h2_connection_failed()`); a GOAWAY
  below a client's stream, or `STREAM_UNPROCESSED`, ends the WebSocket like a reset.
  The adapter copies the DATA it is given, so the h2 connection's buffer may move on.

### Frames (section 5)

- Header: FIN, three reserved bits, a 4-bit opcode, MASK, a 7-, 16- or 64-bit
  length in its shortest form with the top bit clear, and the masking key.
- Opcodes 3 to 7 and 11 to 15 are refused. Control frames are final and carry at
  most 125 octets. A continuation needs a message to continue, and a new text or
  binary frame may not start inside a fragmented message; control frames may
  come between fragments.
- A client's frames are masked and a server's are not, and a frame of the wrong
  kind is refused (section 5.1). Every frame this library sends as a client has
  a fresh four-octet key from the kernel generator (section 10.3).
- A reserved bit is accepted only when a negotiated extension claims it:
  RSV1 for permessage-deflate on the first frame of a data message (not on a
  continuation, not on a control frame), RSV2 and RSV3 as the extension hook says.
  A bit an extension claimed is accepted on every frame, continuations and
  control frames included, because RFC 6455 section 5.2 leaves its meaning to
  the extension; the message event carries the bits of its first frame.

### Messages (sections 5.4 and 8.1)

- A message is delivered whole, once, with its type, the number of frames it
  arrived in, whether it arrived compressed and the RSV2 and RSV3 bits of its
  first frame.
- Text is validated as UTF-8 (RFC 3629: no overlong forms, no surrogates,
  nothing above U+10FFFF) as the octets arrive and across fragments, frames and
  feeds; text this endpoint sends is validated too, and refused with
  `ERR_INVALID`.

### Control frames and closing (sections 5.5 and 7)

- A Ping is delivered and answered with a Pong of the same payload, in order,
  unless this end has sent its Close. A Pong not yet begun to be written is
  replaced by the Pong of a later Ping (section 5.5.3 allows answering only the
  latest), so a reader that is slow cannot be made to queue one Pong per Ping;
  every Ping is still reported. An unsolicited Pong is delivered and
  answered with nothing.
- A Close of no body is reported as 1005; of one octet is an error; with a code
  it must be 1000 to 1003, 1007 to 1014 or 3000 to 4999 (1004, 1005, 1006 and
  1015 are for local use and never on the wire; 1012 to 1014 are the registry's
  service restart, try again later and bad gateway), and its reason must be
  UTF-8 and, with the code, at most 125 octets.
- The reply to a Close carries the code received. A Close the application
  starts with `ghttp_ws_conn_close()` is checked as one received would be.
  The handshake completes once: `GHTTP_WS_STATE_CLOSED` when both have gone.
  Anything that follows the peer's Close, in the same read as the Close or in
  a later one (a whole frame or a single octet), fails the connection with 1002,
  as the story's matrix says, even if the handshake had completed: a feed
  returns the Close and consumes only it, and the next feed with more input
  fails. The failure queues nothing (the Close was sent with the echo) and
  `ghttp_ws_conn_finish()` then reports it, so a closure with trailing bytes
  is not clean. Messages
  that arrive after this end's Close and before the peer's are delivered.
  `ghttp_ws_conn_finish()` says whether the transport ended after a complete
  handshake (1006, which is never sent, otherwise).
- The caller closes the transport; the codec does not know it (the server
  does so first, section 7.1.1).

### Limits (`GHTTP_WsLimits`, defaults)

| Field | Default | Counts |
| --- | --- | --- |
| `max_frame_payload` | 16 MiB | one frame's payload as it arrives (compressed, if it is) |
| `max_message_bytes` | 16 MiB | one message after decompression; also the most a message this end sends |
| `max_fragments` | 1024 | frames in one message |
| `max_control_per_interval` | 128 | control frames received per interval |
| `interval_ms` | 10000 | the interval, renewed only by `ghttp_ws_conn_tick()` |
| `max_buffered_bytes` | 1 MiB | output queued and not taken; at least 131 |
| `max_handshake_bytes` | 8 KiB | the names and values of a handshake's fields |
| `max_extension_offers` | 8 | offers in a handshake (at most 32 are ever read) |
| `max_extension_params` | 8 | parameters of one offer (at most 16 are ever read) |
| `max_expansion_ratio` | 1032 | inflated octets per compressed octet of one message; 0 is no ratio limit |

Every field is a hard cap and a zero is refused (`GHTTP_ERR_INVALID` from every
function that takes limits; the one exception is the ratio, where 0 means no
limit), and a frame may not be allowed to outgrow its message
(`max_frame_payload <= max_message_bytes`). **A connection that is never ticked
has no interval: its control-frame cap is a total for its whole life**, safe
because nothing is left unbounded and wrong for a long-lived connection, which
must tick (`test_ws_conn.cpp` has the never-ticked test).

"Closes before a limit is exceeded by more than one unit" is exact for an
uncompressed message and for the inflated size of a compressed one. What arrives
compressed has the extension's overhead as slack: a compressed frame may be
`max_frame_payload / 64 + 16` octets larger than the limit, and a compressed
message the same of `max_message_bytes`, before 1009.

## Not enforced, or not provided

- **No streaming delivery.** A message is held until it is whole, up to
  `max_message_bytes`; there is no way to receive a message larger than that.
  Sending can be in fragments (`ghttp_ws_conn_send_fragment`) for a message the
  caller produces piecewise.
- **No keepalive, timers or ping scheduling.** The caller decides when to ping.
  The only clock use is the tick that renews the control-frame count.
- **No Origin check and no authentication.** A server that serves browsers must
  check `Origin` itself (cross-site WebSocket hijacking, section 10.2); the
  request is the caller's to inspect before it calls the handshake.
- **No HTTP/3** (RFC 9220 would carry the same adapter), no extension other
  than permessage-deflate (the hook is the seam).
- **No transport rules:** TLS (`wss:`), proxies, URI parsing and the client's
  rule of one connection in `CONNECTING` per host (section 4.1) are the
  caller's.
- **No automatic fragmentation of what is sent.** One call is one frame.

## Extension seams

- **`GHTTP_WsExtensionFn`** is called for each extension the handshake meets
  that is not permessage-deflate (and for it when it is not enabled): the
  server's hook answers with the text of the extension for the response and the
  RSV2 and RSV3 bits it uses, the client's says whether the chosen extension
  is acceptable. The connection lets such a bit through and reports it in
  `GHTTP_WsEvent::rsv`; what it means is the extension's.
- **`GHTTP_WsNegotiated`** is the only thing the connection takes from a
  handshake, so the handshake of Extended CONNECT builds one and the connection
  is unchanged.
- **Limits, options, events and results** begin with a `size` and carry
  reserved members; zero them via the `_default()` functions.
