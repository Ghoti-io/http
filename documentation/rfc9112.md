# What the codec enforces of RFC 9112

**Status:** describes what shipped (version 0.0.0).

This library implements the message syntax and framing of HTTP/1.1, RFC 9112,
with the field and message semantics of RFC 9110 it needs to frame a body. This
page says which rules are enforced, which are not, and where the library
refuses a message that the RFC would let a recipient guess about. Each
enforced rule is tested; the test names are sentences in `tests/unit/`.

A message is refused with one of three results. `GHTTP_ERR_CORRUPT` is bytes
the RFC forbids or that this library will not guess at, `GHTTP_ERR_LIMIT` is a
`GHTTP_Limits` cap exceeded, and `GHTTP_ERR_UNSUPPORTED` is a well-formed
message for a different version. The parser is not recoverable after any of
them, because a recipient that tries to resynchronise inside a stream it has
stopped trusting is how request smuggling works.

## Enforced

### Start line (section 3, section 4)

- A request line is `method SP target SP HTTP-version`, with single spaces. The
  method is a token. The target is not empty and holds visible ASCII only. A
  second space, a tab or a trailing space is `ERR_CORRUPT`.
- The target is one of the four forms of section 3.2, for its method:
  origin-form (`/path?query`), absolute-form (`scheme://...`), authority-form
  (`host:port`, CONNECT only, and CONNECT takes nothing else), and the asterisk
  (`*`, OPTIONS only). Anything else is `ERR_CORRUPT`. The target is kept
  verbatim: it is not percent-decoded, normalised or split beyond the form and,
  for origin-form, the first `?`.
- The version is exactly `HTTP/1.0` or `HTTP/1.1`, upper case. `HTTP/2.0`,
  `HTTP/0.9` and any other well-formed version are `ERR_UNSUPPORTED`, which is
  also what the HTTP/2 connection preface (`PRI * HTTP/2.0`) reports. A string
  that is not a version is `ERR_CORRUPT`.
- A status line is `HTTP-version SP 3DIGIT SP reason`. The space after the code
  is required even when the reason is empty. The code is 100 to 999. The reason
  holds no control character other than a tab.
- Empty lines before a request line are skipped (section 2.2), and counted
  against `max_head_bytes` so that they cannot be sent forever. A response may
  not begin with one.

### Fields (section 5, RFC 9110 section 5)

- A field line is `name ":" OWS value OWS`. The name is a token. Whitespace
  before the colon (section 5.1) is `ERR_CORRUPT`, and so is a line that begins
  with whitespace: an obsolete line fold (section 5.2) is refused, not unfolded.
- A value holds visible characters, space, tab and bytes 0x80 and above. Any
  other control character, including NUL, is `ERR_CORRUPT`. The value is kept
  without leading and trailing whitespace.
- Order, case of names and duplicates are kept. The library does not combine
  fields.

### Line endings

- A line ends with CRLF. A bare LF, and a CR not followed by LF, are
  `ERR_CORRUPT` at the byte, wherever they occur: start line, field, trailer or
  chunk-size line. (Section 2.2 allows a recipient to accept a bare LF; the
  library does not, because a bare LF is the byte two parsers disagree about.)

### Body framing (section 6)

- `Transfer-Encoding` wins over nothing: a message with both it and
  `Content-Length` is `ERR_CORRUPT` (section 6.3 lets a recipient process it;
  the library refuses).
- A `Transfer-Encoding` must name `chunked` exactly once and last, across all of
  its fields and list elements; anything else is `ERR_CORRUPT`. That includes a
  response, where section 6.3 would read it to the end of the connection. Other
  codings before `chunked` (`gzip, chunked`) are accepted and left to the
  caller: the library does not decode content. A transfer coding with
  parameters is not a token and is refused. Empty list elements are ignored.
  `Transfer-Encoding` in an HTTP/1.0 message is `ERR_CORRUPT` (section 6.1).
- A `Content-Length` is one or more digits, or a comma list of them. Identical
  values are one length (section 6.3), so `5, 5` and two fields of `5` are
  accepted; differing values, an empty element, a sign, whitespace inside, or
  any other character is `ERR_CORRUPT`. A value beyond 64 bits is `ERR_LIMIT`,
  but only if no `Transfer-Encoding` is present, since that pairing is the
  smuggling shape and is reported as one.
- A request with neither field has no body. A response with neither runs to the
  end of the connection.
- A response to HEAD, any 1xx, 204 and 304 have no body whatever their fields
  say (section 6.3). A 2xx response to CONNECT starts a tunnel. These need
  `ghttp_parser_expect_response_to()` for HEAD and CONNECT; a response parser
  that is not told treats a response as one to GET. The framing fields of such a
  message are still checked: a conflict in a HEAD response is refused even
  though its body would not be read.
- Chunked bodies (section 7.1): a size in hex digits of either case, leading
  zeros allowed, optional extensions after `;` with optional whitespace before
  it, CRLF; chunk data followed by exactly CRLF; the last chunk is size 0 and is
  followed by trailer fields and an empty line. A size line with no digits, a
  non-hex character, whitespace not followed by `;`, a missing LF, or a control
  character in an extension is `ERR_CORRUPT`. Extensions are skipped and not
  interpreted.
- Trailer fields obey the field rules. A `Content-Length` or `Transfer-Encoding`
  trailer is `ERR_CORRUPT`: framing in a trailer arrives after the body it would
  frame.
- A 101 response and a 2xx response to CONNECT end HTTP reading. After them the
  parser uses no more input.
- An unfinished message when the peer closes (`ghttp_parser_finish`) is
  `ERR_CORRUPT`, and a close-delimited body is complete only then.

### Host (section 3.2, RFC 9110 section 7.2)

- An HTTP/1.1 request with no `Host` field, or with more than one, is
  `ERR_CORRUPT`. The writer refuses to write one for the same reason.

### Limits

`GHTTP_Limits` caps the head (`max_head_bytes`, `max_line_length`,
`max_header_count`), the trailer section (`max_trailer_bytes`,
`max_trailer_count`) and the body (`max_body_bytes`, `max_chunk_size`). A cap
is checked as the bytes arrive, so a line that never ends stops at the cap and
not at the end of the input. Bytes handed out before a cap is hit are the same
however the input was split.

## Not enforced

- **Semantics beyond framing.** The library does not check that a method is
  known, that a status code is registered, that a `Host` value is a valid host,
  that a `Content-Type` parses, or that a header is allowed in a trailer other
  than the two that frame.
- **Content codings, cookies, caching, conditional requests, ranges,
  authentication.** None is interpreted.
- **Connection management.** `Connection: close`, keep-alive, and when to close
  are the caller's. The library reports `Upgrade` and CONNECT and does not
  perform them.
- **`Expect: 100-continue`.** Reported as an ordinary field.
- **Request-target syntax inside its form.** An origin-form target is accepted
  if it begins with `/` and holds visible ASCII; its `%`-escapes, its `#`, its
  dot segments and an empty authority in an absolute-form target are not
  checked. This is the caller's to interpret.
- **Whitespace in a start line.** HTAB as a separator, which section 3 permits a
  recipient to accept in some places, is refused.
- **HTTP/0.9, HTTP/2 and HTTP/3**, WebSocket framing and TLS.
- **Non-ASCII in a target.** Refused rather than interpreted; a caller that
  must accept raw UTF-8 targets has to encode them first.
- **Response without a status reason separator** (`HTTP/1.1 200` with no
  trailing space). Section 4 requires the space and the library holds to it.

## Where the library is stricter than the RFC requires

The RFC lets a recipient accept some of these. Each is a place where two
implementations can legitimately disagree, and an attacker needs only one
disagreement: bare LF and CR, a message with both framing fields, a
`Transfer-Encoding` that does not end in `chunked`, `Transfer-Encoding` in a
HTTP/1.0 message, framing in a trailer, a Host-less 1.1 request, differing
Content-Lengths, obsolete line folding.
